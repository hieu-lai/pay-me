Can one submission intent create agreements exactly once?

Drive a Money Request through browser retries, independent Zepto calls, ambiguous network outcomes, partial success, and operator intervention. The full durable state and evidence trail stay visible after every action.

Question under test. Does this proposed orchestration ensure that the same submission intent never creates duplicate PayTo Agreements, while failures for one Payer never erase or recreate agreements already created for other Payers?
Intent key defines samenessSame key + same payload returns the original Money Request. Same key + changed payload is a conflict.
No heuristic deduplicationA different key is a deliberate new intent, even when the visible details happen to match.
Allocate before calling ZeptoOne transaction creates the Money Request, all one-to-five agreement records, and every stable provider UID.
Ambiguity means GET firstAfter a lost response, duplicate UID, or crash, reconcile by the same UID before another POST.
Payers progress independentlyEvery agreement has its own work, failure, evidence, and retry path. Request progress is derived.
Operator retry is narrowIt reopens one safe agreement using the same local record and UID; it never rewinds created siblings.

What should feel contentious?

Intent boundary. Should a fresh key always mean a fresh Money Request, or should PayMe block lookalike submissions too?
Ambiguous absence. Is a bounded quiet window plus repeated 404 enough before re-POSTing the same UID?
Manual recovery. Should operator retry be allowed only for configuration/manual holds, while immutable-payload failures require a fresh, explicit intent?
Partial failure. Is “two created, one failed” the correct durable outcome, with no all-or-nothing rollback?
